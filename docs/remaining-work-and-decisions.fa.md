# کارهای باقی‌مانده و تصمیمات باز

آخرین ثبت: ۲۰۲۶-۱۱-۱۵. این فهرست، backlog اجرای بعدی است. «نیازمند بررسی» به معنی اثبات وجود باگ نیست. وضعیت‌ها را فقط با لینک commit، تست یا گزارش اجرای قابل بازتولید تغییر دهید.

## تصمیمات باز

«پیشنهاد» تصمیم نهایی نیست. تصمیم را همراه تاریخ، دلیل، دامنه و اثر بر داده/API ثبت کنید.

| شناسه | موضوع | گزینه‌ها | پیشنهاد برای شروع | اثر و زمان تصمیم |
|---|---|---|---|---|
| DEC-01 | پروژهٔ هدف | مخزن/شاخه/revision کاربر | تثبیت SHA پیش از تبدیل | پیش از TODO-03 |
| DEC-02 | سطح سازگاری API | Boilerplate یا Abp | حفظ Boilerplate اگر کلاینت فعلی باید بدون تغییر کار کند | قرارداد endpoint و پاسخ |
| DEC-03 | نوع ارجاع شناسه | Source یا Guid | انتخاب پس از بررسی SQL، کلاینت‌ها و FKهای واقعی | انتقال داده و دامنهٔ تغییرات |
| DEC-04 | migrationها | Squash، Keep یا Delete | برای دیتابیس موجود، آزمایش Squash روی کپی؛ بدون تصمیم خودکار برای production | تاریخچه و داده‌های مستقر |
| DEC-05 | سیاست stub | ممنوع، مجاز صرفاً برای تشخیص، یا مجاز با پذیرش صریح | baseline با `--no-stub`؛ stub تشخیصی جداگانه | جلوگیری از پذیرش ظاهری Build سبز |
| DEC-06 | دامنهٔ اصلاح خودکار | اصلاح محدود یا refactor معماری | مطابق خواستهٔ کاربر: اصلاحات محدود؛ refactor کلی فقط به‌عنوان تصمیم جدا | حفظ منطق پروژه |
| DEC-07 | معیار موفقیت اجرا | Build، runtime یا پذیرش کامل | نتیجهٔ هر سطح جدا و خطای runtime قابل مشاهده برای CI | طراحی گزارش و کد خروجی |

## روش پیگیری هر بخش پروژه

برای هر بخش، نام feature، revision سورس، قاعدهٔ ابزار، خروجی قبل/بعد، خطای build/runtime، تست افزوده‌شده و وضعیت نهایی را ثبت کنید. اگر اصلاح عمومی است ابتدا در موتور اعمال و سپس خروجی دوباره تولید شود؛ اگر مختص کسب‌وکار است در شاخهٔ کاری پروژهٔ خروجی نگهداری شود. کار نیازمند refactor کلی به DEC-06 ارجاع داده شود.

بسته شدن یک مورد به معنی حذف ردیف نیست؛ تاریخ و شاهد نتیجه به آن اضافه شود تا تصمیم‌ها در تبدیل‌های بعدی قابل پیگیری بمانند.
