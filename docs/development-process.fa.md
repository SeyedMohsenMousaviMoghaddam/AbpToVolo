# فرایند تبدیل و توسعهٔ AbpToVolo

تاریخ ثبت: ۲۰۲۶-۱۱-۱۵. مبنای این مستند، کد موجود در شاخهٔ `docs` پس از کامیت اصلاحات `9edbc76` است؛ این متن ادعای بررسی کامل همهٔ قواعد یا تبدیل پروژهٔ اصلی کاربر ندارد.

## هدف و محدوده

ابزار، پروژه‌های ASP.NET Boilerplate با بسته‌های `Abp.*` را به ساختار ABP Framework با بسته‌های `Volo.Abp.*` تبدیل می‌کند. موتور تبدیل فایل‌ها را در خروجی جداگانه بازنویسی می‌کند و گزارش تغییرات، هشدارها و کارهای دستی می‌سازد. تبدیل فرانت‌اند در محدودهٔ فعلی نیست.

سه بخش اجرایی وجود دارد:

| بخش | مسیر | مسئولیت |
|---|---|---|
| موتور | `src/AbpToVolo.Engine` | تشخیص ساختار، بازنویسی، تولید فایل، بررسی و گزارش |
| CLI | `src/AbpToVolo/Program.cs` | تنظیمات، آرگومان‌ها، لغو اجرا و کد خروجی |
| دسکتاپ | `src/AbpToVolo.Desktop` | رابط WinForms و نمایش پیشرفت و نتیجه |
| تست‌ها | `tests/AbpToVolo.Tests` | تست قواعد و تبدیل نمونهٔ موجود |

## ورودی و قرارداد تبدیل

پیش از تبدیل پروژهٔ واقعی، revision ورودی، نسخهٔ بسته‌ها، framework، provider دیتابیس، حالت کلید، سبک API و حالت migration باید مشخص شوند.

| انتخاب | پیش‌فرض فعلی | اثر |
|---|---|---|
| نسخهٔ Volo | `10.7.0` | مقدار موجود در کد؛ به معنی جدیدترین نسخه نیست |
| framework | `net10.0` | framework پروژه‌های خروجی |
| نام لایه‌ها | تغییر نام فعال | Core به Domain و نام‌های مشابه |
| Module Zero | تبدیل فعال | اتصال به ماژول‌های Identity و TenantManagement و سایر وابستگی‌ها |
| Contracts و تست‌ها | تولید فعال | ایجاد پروژه‌های قرارداد و تست |
| شناسه‌ها | `Source` | حفظ نوع برخی ارجاع‌های legacy و اتصال از طریق LegacyId؛ TenantId و فیلدهای audit را جداگانه بررسی کنید |
| API | `Boilerplate` | تلاش برای حفظ مسیرها و envelope قدیمی؛ نیازمند تست قرارداد |
| migration | `Squash` | ادغام migrationهای اولیه با حفظ نقطهٔ ثبت‌شده در state |
| اصلاح با compiler | فعال | چرخهٔ build و اصلاح قواعد شناخته‌شده |
| Build نهایی | در CLI و دسکتاپ فعال | API مستقیم `MigrationOptions.Build` پیش‌فرض false دارد |
| StubUnresolved | در `MigrationSettings` فعال | در API مستقیم `MigrationOptions` پیش‌فرض false است؛ در CLI از `--no-stub` استفاده کنید تا خطا پنهان نشود |
| اجرای DbMigrator/Host | غیرفعال | فقط با گزینه‌های صریح اجرا می‌شود |

این تفاوت پیش‌فرض‌ها هنگام مقایسهٔ اجرای CLI، دسکتاپ و تست‌های API اهمیت دارد. مقادیر واقعی را از `MigrationSettings`، `MigrationOptions` و `Program` بخوانید.

## ترتیب واقعی pipeline

مرجع این جدول [MigrationEngine.cs](../src/AbpToVolo.Engine/Core/MigrationEngine.cs) است. ۲۷ مرحله وجود دارد؛ بعضی مراحل با تنظیمات غیرفعال می‌شوند یا در نبود دادهٔ لازم کاری انجام نمی‌دهند.

| ردیف | کلاس مرحله | مسئولیت اصلی |

| 3 | `RenameLayersStep` | تغییر نام پوشه و پروژه‌های لایه‌ها |
| 4 | `StandardNamesStep` | استانداردسازی نام کلاس‌های ماژول |
| 5 | `ContractsScaffoldStep` | ساخت اسکلت Domain.Shared و Application.Contracts |
| 6 | `LocalizationStep` | انتقال منابع محلی‌سازی XML به JSON |
| 7 | `EfMigrationsStep` | پردازش migrationهای قبلی و کنارگذاری از بازنویسی عمومی |
| 8 | `CSharpCodeStep` | اجرای pipeline بازنویس‌های Roslyn |
| 9 | `ModuleZeroStep` | تبدیل ساختار Module Zero و نگهداری کدهای legacy |
| 10 | `ServiceBasesStep` | تولید یا تطبیق پایه‌های DomainService و AppService |
| 11 | `ContractsStep` | انتقال تعریف‌ها، DTOها و interfaceها به قراردادها |
| 12 | `AbpModulesStep` | وابستگی ماژول‌های Volo و یکپارچه‌سازی DbContext |
| 13 | `LegacyIdStep` | پشتیبانی LegacyId در حالت Source |
| 14 | `ZeroColumnsStep` | حفظ ستون‌های اضافی Zero با mappingهای لازم |
| 15 | `LayerServicesStep` | ثبت سرویس‌های موردنیاز هر لایه |
| 16 | `HostStandardizationStep` | استانداردسازی HttpApi.Host و DbMigrator |
| 17 | `BoilerplateApiStep` | سازگاری مسیرها و پاسخ‌های HTTP قدیمی |
| 18 | `TestProjectsStep` | تولید پروژه‌ها و اسکلت تست خروجی |

| 25 | `ResidualScanStep` | شناسایی باقی‌مانده‌های نیازمند بررسی |
| 26 | `BuildVerificationStep` | Build نهایی و ثبت خطاها |
| 27 | `ReportWriterStep` | ذخیرهٔ state، گزارش Markdown و JSON و قواعد gitignore |

### وابستگی و فعال‌سازی مراحل

Contracts باید پیش از انتقال منابع و کدها آماده باشد. انتقال قراردادها پس از بازنویسی C# انجام می‌شود. تولید Host و تست‌ها به ساختار نهایی لایه‌ها متکی است؛ اصلاح compiler پس از تولید فایل پروژه اجرا می‌شود.

تولید migration ماژول‌های Volo به فعال بودن تبدیل Zero، اصلاح compiler و حالت Squash وابسته است؛ وجود پروژهٔ EF و snapshot و migration مورد انتظار نیز در خود مرحله بررسی می‌شود. ساخت migration با `dotnet ef migrations add` معادل اعمال آن روی دیتابیس نیست.

`HostVerificationStep` در صورت فعال بودن، پیش از Build نهایی اجرا می‌شود. شکست Host، DbMigrator یا endpoint parity در وضعیت فعلی معمولاً به Warning/بخش گزارش می‌رود؛ نتیجهٔ نهایی engine صرفاً از وجود `BuildErrorCount > 0` نیز تأثیر می‌گیرد و یک معیار جامع پذیرش runtime نیست.

## مکانیزم بازنویسی و اصلاح

جدول‌های `Mappings` نگاشت namespace، نوع، بسته و ماژول را نگهداری می‌کنند. `CodeMigration/CSharpFileMigrator.cs` ترتیب بازنویس‌های C# را مشخص می‌کند. کلاس‌های `Steps` عملیات چندفایلی، تولید پروژه و فایل‌های پشتیبان را انجام می‌دهند.

برای توسعهٔ قاعده، ابتدا کوچک‌ترین مثال شکست‌خورده را به تست اضافه کنید. سپس mapping یا rewriter نزدیک به مسئله را تغییر دهید؛ اگر مسئله به چند پروژه یا تولید فایل مربوط است، مرحلهٔ مناسب را توسعه دهید. پس از تغییر ترتیب، وابستگی داده‌های مراحل بعدی را بررسی کنید.

`BuildFixStep` حداکثر ۱۰ دور معمول و در حالت stub حداکثر ۴۰ دور دارد؛ بعضی خطاهای محیطی نیز مسیر retry دارند. گزینهٔ stub می‌تواند بدنه‌ها را زیر `ABPTOVOLO_ORIGINAL` نگه دارد و کد جایگزین بسازد. برای برخی اعضای startup رفتار جایگزین می‌تواند رد کردن اجرا باشد، نه پرتاب خطا. پس «Build موفق» تضمین اجرای منطق کسب‌وکار نیست.

## حفاظت ورودی و خروجی

در اصلاح اخیر، مسیرهای ورودی و خروجی پس از بررسی لینک‌های اجزای مسیر مقایسه می‌شوند. مساوی بودن یا دربرگرفتن یکی توسط دیگری رد می‌شود؛ جداکنندهٔ انتهایی مسیر نیز لحاظ می‌شود. زیرپوشه‌ها و فایل‌های لینک‌دارِ غیرمستثنا در سورس، پیش از پاک‌سازی خروجی رد می‌شوند؛ پوشه‌های ignored مانند bin، obj و git کپی نمی‌شوند.

`--force` خروجی را بازسازی می‌کند و پوشه‌های تعیین‌شده در `KeptFolders` مانند `.git`، `.abptovolo` و `.vs` حفظ می‌شوند. این رفتار یک merge هوشمند با ویرایش‌های دستی خروجی نیست. لاگ فقط پس از موفقیت مرحلهٔ کپی داخل خروجی باز می‌شود؛ در شکست زودهنگام از محل موقت استفاده می‌شود.

این کنترل‌ها جایگزین snapshot و بررسی diff نیستند؛ کپی و پاک‌سازی هنوز تراکنش فایل‌سیستمی با rollback کامل ندارند.

## state و تبدیل مجدد

فایل `.abptovolo/state.json` نقطهٔ squash، شناسه‌های migration تولیدشده، SourceRevision و اطلاعات لازم برای تکرار تبدیل، از جمله passphrase تولیدشده، را نگه می‌دارد. سیاست نگهداری و محرمانگی آن باید پیش از استفادهٔ واقعی مشخص شود؛ فایل را کورکورانه در مخزن عمومی منتشر نکنید.

در پروژهٔ خروجی، شاخهٔ `converted` را برای خروجی خالص ابزار و یک شاخهٔ کاری جدا را برای اصلاحات دستی نگه دارید. تبدیل مجدد را روی شاخهٔ خروجی خالص اجرا و commit کنید، سپس با merge سه‌طرفه وارد شاخهٔ کاری کنید. state قبلی باید حفظ شود. migrationهای جدید سورس بعد از نقطهٔ squash به بازبینی و تولید migration مناسب در شاخهٔ کاری نیاز دارند.

## اجرا و اعتبارسنجی

از ریشهٔ مخزن:

```bash
dotnet test tests/AbpToVolo.Tests/AbpToVolo.Tests.csproj --nologo
dotnet build src/AbpToVolo.Desktop/AbpToVolo.Desktop.csproj --nologo
```

Build دسکتاپ روی ویندوز انجام می‌شود؛ برای صرفاً cross-build در لینوکس، `-p:EnableWindowsTargeting=true` لازم است. این کار تست اجرای رابط WinForms نیست.

برای تبدیل آزمایشی بدون stub، مسیر خروجی جداگانه انتخاب کنید:

```bash
dotnet run --project src/AbpToVolo -- samples/Acme.PhoneBook -o ../out/PhoneBook --no-stub
```

نسخهٔ هدف را با گزینه‌های `--abp-version`، `--framework` و در صورت نیاز `--ms-version` صریح ثبت کنید. برای اعمال دیتابیس و اجرای Host، گزینه‌ها را فقط با تنظیمات یک محیط آزمایشی دارای دیتابیس کپی‌شده اضافه کنید. `--no-build` فقط Build نهایی را غیرفعال می‌کند؛ برای غیرفعال کردن چرخهٔ compiler از `--no-compiler-fixes` نیز استفاده کنید.

خروجی‌ها شامل `ABP-MIGRATION-REPORT.md`، `abp-migration-report.json`، `abp-migration.log` و state هستند. نتیجه را در چهار سطح جدا ثبت کنید: تست ابزار، Build و تست خروجی تبدیل‌شده، صحت انتقال داده و اجرای سرویس، و پذیرش سناریوهای کسب‌وکار.

## اصلاحات و شواهد این مرحله

کامیت `9edbc76` شامل حفاظت از مسیر و لاگ، پشتیبانی از لغو در کپی و Build نهایی، ثبت شکست Build بدون diagnostic استاندارد، کد خروجی CLI و نمایش هشدار دسکتاپ، تست‌های بازگشتی و workflow تست است.

| بررسی انجام‌شده | نتیجه |
|---|---|
| تست‌های ابزار با SDK 10.0.100 | ۱۳۳ موفق، صفر شکست، صفر skip |
| cross-build نسخهٔ دسکتاپ | صفر خطا و صفر هشدار |
| بررسی whitespace با `git diff --check` | موفق |
| اجرای UI دسکتاپ روی ویندوز | در این بررسی اجرا نشده |
| Build و تست زندهٔ خروجی Volo و انتقال SQL Server | در این بررسی اجرا نشده |
| GitHub Actions اضافه‌شده | برای PR و push به main تنظیم شده؛ اجرای آن در این مرحله ادعا نمی‌شود |

تست‌های تبدیل نمونه در مجموعهٔ ابزار را با تست یک خروجی واقعی Volo اشتباه نگیرید. اعداد یا نتایج تاریخی README نیز شواهد اجرای فعلی نیستند.

## معیار افزودن قابلیت جدید

هر اصلاح باید یک مسئلهٔ قابل بازتولید، تست رفتاری یا نمونهٔ معنی‌دار، تغییر محدود، و نتیجهٔ آزمون داشته باشد. برای runtime یا دیتابیس، تست همان لایه نیز لازم است. تغییراتی که مدل کسب‌وکار یا معماری را جابه‌جا می‌کنند، پیش از اجرا به‌عنوان تصمیم باز ثبت شوند. فهرست پیگیری در [کارهای باقی‌مانده و تصمیمات باز](remaining-work-and-decisions.fa.md) است.
